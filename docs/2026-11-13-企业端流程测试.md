# 企业端完整流程测试与改进建议

测试日期：2026-11-13。范围为企业进入、应届岗位发布、能力与背景条件、投递授权、三类面试、候选人管理、招聘资源规划。此次仅新增测试脚本、截图与报告，未修改业务实现、正式数据库、模型配置或现有服务，未提交和推送。

## 结论

企业端已经具备可演示的“发布岗位 → 学生看到岗位并授权投递 → 企业查看资料 → 独立场景测评与人工复核 → 双向选择 → 预算约束分配”主干。真实新企业需要自行创建岗位与等待学生投递；免登录演示预置8个岗位、15名候选人、45份投递和12组双向意向，不能用演示空间的数据丰富程度代表新账号开箱状态。

当前最先应修复的是招聘业务状态与分配算法脱节：已经标记“暂不合适”的候选人、已经结束的岗位仍进入招聘分配。预设面试完成后回答没有接入企业复核使用的数据，学生必须在另一个入口重复作答。真人面试存在真实 WebRTC 音频实现；主流程接通失败，专项两轮收到了音频包，但仍频繁409且企业界面报错，尚不能按稳定线上面试验收。AI本次只验证无配置失败与授权边界，未消耗模型API，未验证真实模型追问质量。

## 问题清单

### E01 · P1 · 已淘汰候选人与已结束岗位仍被分配（真实UI复现）

复现步骤：创建岗位，学生授权投递、提交对应能力场景题，企业完整复核并选择学生；进入“招聘分析与分配”，输入16000/1000/10预算计算，得到1个候选对；进入候选人主页把阶段改为“暂不合适”，重新计算，仍得到相同1人；进入岗位管理把岗位改为“已结束”，再次计算，仍得到相同1人。

实测结果：三次均占用月薪16000、培训1000、导师10课时。证据`results.json:allocation_before_stage / allocation_after_decline / allocation_after_close`、`06-declined-closed-still-selected.png`。

原因：`backend/app.py:475`的分配接口在477行收集本企业全部岗位，在481行仅排除撤回的投递，483行未传递招聘阶段/岗位状态；`backend/matching.py:173`在174行只检查`eligible`与双向意向。`backend/recruiting.py:118`至127行更新招聘阶段时只写`stage`，没有与意向或分配资格同步。

影响：企业明确淘汰的候选人和停止招聘的岗位会继续占用建议预算，使“动态规划”结果与企业操作矛盾。

建议：先定义阶段和岗位状态对分配的准确契约，在服务端构建候选集合时统一过滤；关闭/淘汰后的既有结果标记过期并说明原因。覆盖“淘汰、暂停、结束后不得新增分配”的真实集成测试，同时区分已入职实际成本与待分配预算。

### E02 · P1 · 完成预设面试未形成可复核回答，面试与测评断链（真实UI复现）

复现步骤：学生投递带2道预设题的岗位，在投递记录进入“语音面试”→“企业预设问题”，用文字完成2轮回答；企业进入“测评复核”。

实测结果：面试会话`completed=true`，记录2条学生回答；对应`application.answers={}`。企业复核入口依赖的答案仍为空。为了完成预算主流程，本次必须回到学生“参加测评”，再次填入回答后才能复核。证据`04-preset-completed.png`、`results.json:preset_interview`。

原因：`backend/experience_api.py:203`的`turn`在213—229行仅维护面试消息及完成状态。`web/workflows.js:104`的复核入口从`application.answers`渲染回答；`backend/app.py:452`附近要求复核引用已回答且关联该能力的题目。界面提示“回答已记录，你可以核对后提交给企业”，却没有将这些会话回答确认提交到测评证据的入口。

影响：学生认为已经完成企业问题，企业依然无法按当前证据校验流程复核，造成重复输入，面试收益不能进入匹配和规划。

建议：统一问题标识与回答证据。预设面试结束后提供“核对并提交企业复核”，复用既有答案版本、授权与历史快照机制。AI/真人会话的总结需经学生确认形成关联证据，企业才可引用复核。

### E03 · P1 · 真人音频有收发实现，但信令竞争导致失败或连接后界面报错（真实双端浏览器复现）

复现步骤：学生从已投递岗位创建“真人面试官”会话；企业打开候选人→面试会话→进入；双方点击“接通音频”。两侧使用独立Edge上下文与合成麦克风，未用假接口替代信令。

主流程实测：学生显示“面试内容已更新，请重新打开”，企业显示“通话轮次已变化，请重新接通”，均没有进入“真人音频已接通”。证据`08-human-audio-desktop.png`、`results.json:human_audio`。

专项复核两次新会话：按“学生offer完成后企业加入”和“近同时点击”两种顺序，双方底层`connectionState`最终均为`connected`，音频`inbound-rtp`分别收到约46—48KB、780—792包，证实本机双端音频实际收发。但两轮32/33条信令分别发生18/19次409；两轮企业界面最终仍显示“本轮操作未完成，可以重试”，双方错误区均保留“面试内容已更新，请重新打开”。因此既存在失败，也存在音频已经连接而界面持续报错的状态失真。证据`human-results.json`、`13-human-*.png`；合成设备数据不能替代真人实际听音验收。

实现确实包含音频：`web/voice.js:137`获取音频设备，143行创建`RTCPeerConnection`，147行接收远端音轨；后端`backend/experience_api.py:232`至252行持久化offer/answer/candidate信令。这不是仅有占位按钮。

根因定位：`web/voice.js:129`的每条信令独立执行“读取revision → POST更新”，ICE候选回调可能并发；后端使用会话整体revision乐观锁（`backend/experience_api.py:148`、`251`），且通话轮次与消息共用同一会话更新。信令重试耗尽后调用`showError`，轮询异常分支则会`stopVoice`；已连接的音频和错误提示缺少一致的状态管理。专项接口时序已直接捕获大量整体revision冲突，不属于仅从界面推测原因。

影响：路演现场双端音频可能在双方接通时失败；仅展示“真人面试”入口不足以证明可用。

建议：先修复同一会话信令的并发写入和重试协议，独立管理信令序号/通话轮次，避免整体会话revision竞争；完成双端浏览器真实音轨收发测试。随后测试跨网ICE能力。当前`iceServers:[]`只有主机候选，未配置STUN/TURN（`web/voice.js:143`），本次局域同机结果不代表公网可达。当前实现为音频，未提供视频。

### E04 · P1 · “面向应届生”没有资格字段和校验（真实UI确认 + 数据结构核查）

复现步骤：企业发布岗位时检查所有可填条件；学生查看基本画像与投递流程。只能在岗位名称/JD写“应届生”，没有毕业年份、毕业时间范围、在读/已毕业状态或允许年级字段；学生画像也没有对应信息。

证据：`results.json:job_form_fields / profile_form_fields / student_visibility_and_apply`。`backend/schemas.py:48`的硬背景只有专业、院校、语言；`113`的学生画像未建毕业信息；`backend/app.py:374`的投递接口检查岗位开放、资料归属和重复投递，没有应届资格检查。

影响：系统能够发布写着“应届生”的JD，但无法对目标毕业人群做结构化筛选、校验或可解释的资格提醒。

建议：以校招最小必要信息定义毕业时间、当前学业状态、岗位允许毕业届别，展示候选人资格与证据状态。沿用必要条件“通过/待核实/不满足”的机制，在学生授权时说明用途。

### E05 · P1 · 企业不能发起面试邀约，招聘排期与结果闭环不完整（真实入口确认 + 代码核查）

复现步骤：新投递后，企业从候选人进入“面试会话”，页面提示“等待学生创建面试会话”。企业仅能进入学生已创建的会话。

证据：`results.json:empty_interview_list`、`web/voice.js:123`；`backend/experience_api.py:178`的创建接口在179行限制学生身份。当前会话没有时间、时区、预约确认、面试官、通知状态等结构化字段。`backend/recruiting.py:27`的招聘阶段只有新投递/评估/面试/已发意向/暂不合适；修改阶段只保存字符串，无录用接受、入职与名额占用联动。

影响：可以站内文字商量时间，不能按当前实现宣称已经实现企业邀约、排期通知、录用落实的完整招聘管线。这里的“已发意向”是管理标签，不能等同学生收到并接受正式offer。

建议：优先建立站内面试邀约与确认、双方可见的时间和状态；把面试记录、意向、接受/拒绝、完成录用与岗位剩余名额连接起来。外部邮件/短信发送属于单独授权范围，此次未发送。

### E06 · P2 · 动态招聘规划目前是一次计算，缺少可保存和比较的计划（真实UI + 代码核查）

复现步骤：在“招聘分析与分配”输入预算并计算，切换页面再回来。表单与计算结果重新创建，新企业没有已保存预算或方案入口。

原因：`web/views.js:38`直接生成空预算表单，`web/workflows.js:119`仅将响应拼入当前DOM；`backend/app.py:475`直接返回`allocate`结果，未保存计划、预算版本、选中名单与假设。`web/recruiting.js:85`至89行只在演示空间按岗位数据预填预算。

影响：能够证明预算约束优化有实现，但难以向企业说明“上周计划与今天变化”、候选人不足的缺口、预算调整带来的收益和已有招聘承诺占用。

建议：最小方案包括保存预算与分配版本、显示计划时间和输入快照、按真实姓名/岗位展示选中者、对比一次预算调整前后差异、标出未选原因。先修E01再扩大规划功能。

### E07 · P2 · 新企业全零阶段图仍画成五块等分环图（实际显示确认）

复现步骤：注册没有任何投递的新企业，进入招聘总览。四项数字均0，但招聘阶段图显示五个占比相同的彩色扇区，每个标0份。

证据：`01-empty-employer-desktop.png`。`web/recruiting.js:101`对全零数据仍使用饼图；未提供全零空态，也没有关闭全零等分显示。

影响：第一屏看似已有阶段结构，视觉比例与“没有数据”含义不一致。

建议：无投递时显示空态和下一步操作，产生第一份投递后再显示真实阶段比例。

### E08 · P2 · 能力要求可动态增减，但熟练程度与测评完整性未形成可执行配置（UI及代码核查）

已验证可维护技能名称、类别、必要标记、对应测评题，并可从招聘偏好页面调整关注程度。用户无法在当前岗位编辑表单中设置“需要达到几级”；`web/workflows.js:5`与19行只读取skill/category/mandatory，未读target；服务端`backend/schemas.py:32`默认target=3。

另外，`backend/schemas.py:54`允许questions为空，校验仅检查已给题目的技能是否属于岗位；没有要求每项待复核能力存在关联问题。结合E02与企业复核“必须引用该能力已作答题目”的规则，岗位可以发布成功，却缺少完成证据核验的路径。这一项未另造缺题岗位做UI实验，属于代码推断，与已实测E02分开记录。

建议：用业务化等级描述配置目标熟练度；岗位发布时提示没有测评或可核验证据路径的必要能力。默认值需要对企业可理解，避免仅靠后台数字决定必要门槛。

## AI与授权边界的准确表述

AI面试在界面要求学生明确勾选将转写发送给DeepSeek；未同意时提示确认；空密钥时显示明确配置错误，原回答仍保留。`backend/experience_api.py:220`至228行实际调用`agent_run`，没有以固定回复冒充模型完成。此次未执行真实DeepSeek调用，不能宣称模型内容质量、延迟与故障恢复均已通过。

岗位内容更新与撤回授权是两种不同操作：更新岗位会清空复核并重置双方意向，**没有撤回学生已授予的资料访问权**；真实撤回后材料和面试立即403。这一行为已实测，不能把“版本更新清复核”写成“资料授权已撤销”。
