# 高校与企业完整流程系统测试、问题与改进建议

测试日期：2026-11-13。代码基线：当前工作区，测试开始时Git已跟踪业务代码无未提交修改。业务测试使用独立SQLite及文件目录，真实Edge浏览器；本轮未修改业务逻辑、正式资料或模型配置，未提交、推送及部署。实际修改为企业Logo资产及来源登记，并新增本报告。

## 结论

系统已经具备真实可运行的课程导入、约束计算、条件情景预测、图文报告、岗位发布、授权投递、人工复核和双向分配。图表具有实际Canvas和数据联动实现。当前最影响评委、投资人判断的，是**跨模块流程没有连接完整、部分业务状态没有进入计算、输入准备依赖技术人员**。

在预先准备的结构化数据下，可以完成高校决策与报告；普通高校从上传课表和培养文件开始，还不能顺畅完成同一个业务项目的报告。企业发布、投递和独立测评可走通，但预设面试没有进入复核，关闭/淘汰状态没有进入分配过滤，真人面试存在信令冲突。当前适合展示已核验路径和条件计算；“两端均可从零自助完成全流程且稳定”尚不符合本轮结果。

第一性原理下，验收应围绕五件事：用户能表达目标；系统能将已有资料变成可确认输入；操作和业务状态能连续流转；输出可追溯到本项目的输入与约束；最终结果能带走、能再次调整和复算。单个按钮、图表或API存在，不能替代这些验收。

## 测试方法、范围与已通过部分

### 实际操作

高校使用全新账号，从页面注册开始，导入用户确认的真实全校课表，浏览课程库并从界面下载XLSX，再用合成资源假设从课程库选择候选、完成简版优化；随后从界面登记合成研究来源、导入招聘/就业JSON、创建专业决策、计算、切换情景并导出报告。最后建立第二个零预算项目，检查项目切换与无改善结果。

企业使用独立企业/学生上下文，从注册、发布岗位、学生填写基本信息、上传测试简历、授权投递、预设面试、独立场景测评、企业复核、双向选择、预算计算，到淘汰候选人、关闭岗位、版本更新和撤回授权。真人音频另做两轮双端真实WebRTC验证。

所有培养效果、岗位、候选人经历、资源和能力增益均为明确标记的隔离合成输入；真实课表仅用于验证文件识别与课程导出。本次没有真实DeepSeek生成调用，未录制真人麦克风，未验收公网AWS或真实手机。真人专项使用浏览器合成音频设备，检查真实音轨收发和信令，不代表真人听音或跨网验收。

## 高校端：问题、原因、建议和验收

### U01 · P1 · 培养方案优化结果没有进入图文报告

**复现**：新高校导入736门课→“培养方案优化”填写缺口、预算等约束→从课程库选课→计算成功并提示保存→“高校培养诊断”。

**实测**：优化历史已有1次、选中1项课程；报告的`program`仍为null、`actions=[]`、`source.run_id=null`，五项指标和预测继续待补充。已有专业决策的账号则继续读取旧决策，简版优化同样不会替换报告输入。

**原因**：`backend/app.py:569`保存实体`optimization`；`backend/university_report.py:25`只读取`university_profile`和最新`decision_run`。前端`web/curriculum.js`计算后只更新简版结果。两条有效计算路径没有共同的报告引用。

**建议与验收**：建立当前培养项目、输入版本和选定计算结果的统一引用；保留现有计算引擎，增加报告适配。用户完成一次优化后能直接打开同一项目的报告；预算、课程动作、来源版本与刚才输入一致，不再次手写配置。证据：`university/journey.json:optimization-report-disconnection`、截图04/05。

### U02 · P1 · 培养方案上传与专业决策之间缺少结构化确认流程

**复现**：上传本校课表，再从“上传培养方案”上传含培养目标、学分与预算的测试正文；进入专业调整决策建立项目。

**实测**：培养文件保存为参考正文，返回`imported_courses=0`，报告的专业方案仍为空；建立决策先提示“请先导入用于方案开发的招聘证据”。完成研究数据导入后，还必须上传包含`program/actions`的JSON。当前创建弹窗有31个控件，其中26个必填；JSON内部课程、技能证据、方向、分组、约束等不计入这26项。

**原因**：`backend/university_courses.py:67`的文档分支只保存正文；JSON课程分支只取课程列表。`web/competition.js:50`的决策创建依赖外部配置文件，没有将课程库/培养正文转成可确认的专业配置表。

**建议与验收**：增加“选专业与岗位目标→选本专业课程→核对提取字段→补缺项”的表单。抽取结果附原文位置，由教师确认；技术JSON保留为高级导入选项。普通用户无需编辑JSON即可创建一个有效项目。证据：`program-document-import`、`decision-blocked-after-course-import`、`advanced-structured-flow-success.decision_form`。

### U03 · P1 · 查看项目A，报告却显示最新运行的项目B

**复现**：运行A“能力提升”；再运行B“零预算”；返回A“查看结果”，再进入高校培养诊断。

**实测**：决策页正在显示A的结果，报告仍返回B的run_id和专业B。无法从报告选择A。

**原因**：`backend/university_report.py:29`直接使用`store.list('decision_run', owner)[0]`，报告接口没有项目/结果参数；查看结果没有改变报告选择。

**建议与验收**：报告以`case_id/run_id`明确选择，标题显示专业、版本与时间；从任意决策结果进入报告应沿用该结果。两个项目来回查看，预算、课程与图表都不串项目。证据：`project-selection-mismatch`，截图09。

### U04 · P1 · 本校缺口接口把草稿、暂停、结束和删除岗位纳入目标

**复现**：建立5名真实注册的隔离本校学生，SQL均2级；发布SQL目标3级岗位，再放入一个目标5级的非招聘岗位。分别设其为draft/paused/closed/deleted。

**实测**：四种状态下，“使用本校汇总缺口”读取的`/university/insights`目标均4、缺口2；需求研判与报告目标仍3，真实活动岗位对应缺口1。

**原因**：`backend/app.py:554`遍历所有job，未过滤业务状态；`backend/university_intelligence.py:218`与报告已过滤，三个入口口径分叉。

**建议与验收**：共用活动岗位筛选与技能标准化规则；为缺口保留城市/赛道/专业范围。暂停、结束、删除岗位均不再改变可选课程的目标；三个页面同范围目标一致。证据：`university/boundaries.json:inactive_jobs`。

### U05 · P1 · 可视化报告无法直接导出成同等质量的交付件

**复现**：完整计算后进入图文报告，展开底部“课程明细、数据来源与测算依据”，点击导出。

**实测**：仅导出Markdown正文，包含多段原始JSON，不包含图像；`format=pdf`返回422。图文报告高度约3,944px，导出入口位于底部折叠区，首屏无报告导出按钮。

**原因**：`backend/competition_api.py:59`和279行只实现JSON/CSV/MD；图表在浏览器Canvas中绘制，没有报告导出/打印排版。

**建议与验收**：报告顶部加入“导出图文报告”；先实现稳定打印版或HTML/PDF，包含当前情景、曲线、资源图、课程前后表、假设与出处。浏览器里看到的本项目关键内容应完整进入交付件，图表不丢失。证据：`report-export`及`报告正文-隔离验证.md`。

### U06 · P1 · 目标、候选课程与效果假设主要依赖事先准备，个性化产出不足

**核查**：当前能输入资源上限和能力缺口，但没有结构化的“优先补哪类岗位/技能、招生保持范围、优先控成本”等高校目标选择；高级页面要求使用者提供候选课程动作及`skill_delta`。算法在这些候选中计算，能力改善和就业弹性来自显式假设。

**影响**：教师知道自己的业务目标，也难以自己形成第一份可计算输入；若候选课程和能力增益准备不充分，图表完整也无法提高建议质量。当前输出不应被解释为系统已从课表独立学得课程教学效果。

**建议与验收**：用业务语言记录目标和保护项，并把它们映射到现有求解条件；从已确认课程—技能映射提出候选，给出依据、投入、先修、考核方式，教师核准增益范围。以同一课程基础分别选择“优先补核心技能”和“预算压缩”，输出应按目标产生可解释差异。保留假设与实际毕业跟踪的区分。

### U07 · P2 · 一门课程缺映射，会使全部课程覆盖数消失

**复现与实测**：课程库只有一门映射到SQL的课时，SQL覆盖数为1；再导入一门尚未映射的课，SQL及其余技能的覆盖数全部变为null。

**原因**：`backend/university_intelligence.py:124`的`_courses`遇到任意未映射课程就返回None。实际全校736门目前均缺映射，课程库界面又没有逐门补学时、确认映射的编辑入口，主要依赖重新上传文件。

**建议与验收**：显示“已确认至少1门；另1门待映射”，附已映射比例；支持搜索后逐门/批量核对。部分完成应立即有可用价值，不把未知当0，也不清空已确认部分。证据：`boundaries.json:partial_mapping`。

### U08 · P2 · 新高校首页首要操作在七张图之后

**实测**：1440×900首屏是0公告、0岗位、0企业、样本不足；首个“导入本校课程”按钮纵坐标约3,241px，首页总高约3,605px。新用户需先经过大量空图，或从侧栏另找资料库。

**原因**：`web/university-intelligence.js:40`先渲染七个图面板，下一步CTA放在41行的末段。

**建议与验收**：首屏给出当前项目、资料完成度和一个主要下一步；无资料时突出导入/选专业，已有结果时突出查看/调整报告。保持液态毛玻璃视觉，减少初始空图。新高校在不滚动时可以开始准备方案。证据：`new-school-entry`、截图01。

### U09 · P2 · 无改善方案时没有明确呈现当前约束导致的失败

**实测**：项目B预算0，唯一新增动作成本5,000，决策结果为`no_improving_plan`。报告继续列出该动作并标“待测算候选建议”，未把“已测算但当前不可选”作为主要结论；预测缺项提示回到通用补齐输入说明。

**原因**：报告只在有`best`时提取结果，其他情况统一回落到原始候选；`forecast_reason`使用缺输入默认文案，未对应完整决策状态与轮次反思。

**建议与验收**：输出“预算不足，差额5,000元”等可执行原因、冲突资源和可调整项；区分未算/无可行解/无正改善/成功。零预算项目应明确解释原因，不能像尚未测算一样列建议。证据：第二项目与截图09；`backend/university_report.py:126`、144行。

### U10 · P2 · 详细教学建议使用固定模板，缺少课程特异性

**核查**：`web/university-report.js:33`按固定12.5%/25%/37.5%/剩余比例拆分学时，按技能关键词生成练习；实施路径统一四学年文本。实际课程大纲、现有教学模块、课程学期与考核依据没有参与这部分文本生成。

**建议与验收**：每门调整课程展示旧模块→新模块、对应技能证据、真实项目任务、先修与学期、验收作品及师资；模块学时与资源上限一致。不同课程和调整类型应有不同内容；无法提取的字段显示待确认。固定模板可作为初稿，不应承担最终课程方案。

### U11 · P2 · 报告使用历史快照，但缺少明显的变更与重算提示

**核查**：一旦存在决策run，报告一直使用其case/证据快照。之后再上传培养文件、更新全校课程库或执行简版优化，不会成为该run的新输入。页上显示测算日期，但没有输入变更差异和过期状态。

**建议与验收**：保留已审核快照，并显示“课程/岗位/资源已更新，报告仍基于版本X”；提供确认差异后重算。新上传应进入当前项目的待确认输入，不直接悄悄覆盖结果。证据：`backend/university_report.py:33`与U01完整链路。

### U12 · P2 · 重点信息字号偏小，长报告和固定挂件增加阅读成本

**实测与核查**：移动报告无横向溢出，指标说明字号为11px；五项指标、假设和实施文字密集。桌面首屏固定Agent挂件与最右实施成本卡片重叠，完整报告截图能看到金额右侧被角色遮挡。`web/role-mascots.css:8`定义92×108固定入口，报告对该覆盖区域没有避让。

**建议与验收**：首屏集中展示三条结论、最重要的调整及预算，完整依据折叠；增加关键说明字号，挂件对重要指标/输入自动避让或收为小入口。保留玻璃视觉和Canvas图表；在1440×900及390×844截图和元素点击测试中，KPI、下一步按钮与输入均不被遮挡。

## 为什么输出质量会不稳定

1. **输入缺少决策必需事实。** 全校课表能提供课程名称、代码、学分、院系和校区；本次真实文件没有总学时和能力映射，也不含能力增益、就业去向、同范围年度需求人数。需要明确补哪些数据以及如何确认，不能靠把公告数当人数来补齐预测。
2. **计算对象分散。** 课程目录、专业方案、简版优化、专业决策与报告分别存储；招聘阶段、意向、测评答案和面试会话也各自维护。单模块正常，跨模块不一定承接。
3. **人的目标没有充分进入可计算条件。** 目前主要在既定候选动作、给定增益和参数内优化。候选本身和参数证据若薄弱，模型无法自动补出高质量教学设计。
4. **展示和结果状态对应不足。** 报告默认取最新run、无解回落候选、已结束岗位仍参与分配、音频连接但UI报错，都使用户难以判断当前结果是否属于自己的有效操作。
5. **可视化与可交付分离。** 页面Canvas能显示，导出仍是JSON密集的MD，企业计划又未持久化；会影响评委“这份成果是否能拿回去继续使用”的判断。

## 建议的实施顺序与现场验收

**第一批：修复结果正确性和流程断点。** U01统一项目到报告的承接；U03明确报告run选择；U04统一活动岗位口径；E01状态进入分配；E02面试证据进入复核；E03稳定音频信令。每项用本轮复现脚本变成针对性回归，修复后核验真实双端行为。上述事项完成前，不扩大算法或动效范围。

**第二批：让非技术用户独立完成。** U02培养配置确认表、U06目标与候选建议、U05图文导出、E04应届资格、E05企业邀约、E06计划保存比较。保留底层真实计算与数据依据，把JSON、技术参数移到高级区。

**第三批：提升路演表达。** 首页变为“当前进度+下一步”；空图、11px说明、挂件遮挡、课程映射进度、无解说明逐项优化。只增加能解释结论的图，不靠增加图表数量替代流程。

建议以以下现场任务验收，而非只沿固定预置脚本展示：

| 现场任务 | 完成判据 |
|---|---|
| 评委临时改高校预算/师资 | 同一项目重新计算，报告同步更新；说明选中/取消哪门课、为什么、资源差多少 |
| 评委在两个专业间切换 | 报告名称、课程、约束与来源始终属于选中的专业和版本 |
| 从真实课表开始 | 展示识别计数、缺项及教师确认；无需编辑JSON即可继续准备有效输入 |
| 导出学校报告 | 带走与当前情景一致的图文文件，包含前后对比、四年曲线、课程建议、假设及来源 |
| 企业发布应届岗位 | 学生实际看到，目标毕业人群可识别，软/硬要求及未核实项清楚 |
| 学生参加一次面试 | 回答确认提交后企业直接复核，无重复填写；复核结果进入匹配与规划 |
| 企业淘汰/关闭后重算 | 对应候选与岗位不再新增占用预算，计划差异可解释、可保存 |
| 双端线上面试 | 两端可接通、挂断、重连，实际音轨有收发且界面一致；跨网结果单独验收 |

预置演示可以展示丰富度；新账号操作应展示数据如何真实产生。企业演示当前8岗、15候选、45投递、12双向意向，属于隔离演示资料，不代表平台已有真实客户和招聘成交。本轮建议现场先展示已经核验的发布→授权→独立测评→人工复核→双向选择→开放岗位分配；面试断链与音频稳定问题修复后再串成一条完整演示。
